# PowerRanking 架构升级设计（UPGRADE_DESIGN）

- 阶段：只读设计，不修改任何源码/配置/存档，不编译。
- 目标：降低 CPU/GC 占用，并将「简单权重百分比相加」升级为更科学的综合国力评价模型，同时保持功能与 UI 不变、避免无关重构。

---

## 1. 当前架构的问题

（详见 `AUDIT_REPORT.md`，此处只列与本次升级直接相关的）

1. **多趟遍历**：`Compute()` 里每个国家分别调用 `countTotalWarriors()`、`countZones()`、`countCities()`、`getPopulationPeople()`、`CountEconomy()`，城市被遍历约 4 次、单位 1~2 次（对应审计 M2）。
2. **归一化脆弱**：当前 `min-max` 对单个极端值敏感；无差异时返回 0.5，导致单国恒 50 分（审计 L1）。
3. **评分/采集耦合**：采集、归一化、排序、UI 重建都堆在 `Compute()` 和 `RebuildRows()` 里，难维护、难测试。
4. **UI 全量重建**：每次刷新/点击销毁重建所有行（审计 M3）。
5. **无缓存与变更检测**：世界稳定时仍每 3 秒全量重算并重建 UI。

## 2. 新算法设计

### 2.1 六个维度（全部基于已验证的真实游戏 API）

| 维度 | 原始数据来源 | 说明 |
| --- | --- | --- |
| 军事 military | `Kingdom.countTotalWarriors()` | 战士数量 |
| 经济 economy | 全国单位 `money + loot` 之和 | 无国库字段，沿用现有真实代理 |
| 人口 population | `Kingdom.getPopulationPeople()` | 总人口 |
| 领土 territory | `Kingdom.countZones()` | 1 zone = 64×64 格 |
| 城市发展 development | `countCities()` + 各城 `buildings.Count` 之和 | 城市数量 + 建筑量，表示城市化程度 |
| 国家影响力 influence | `Kingdom.getRenown()` | 名望 |

说明：`development` 用「城市数 + 建筑数」作为城市化/发展水平的可解释代理；两个量级不同，由对数压缩统一。所有数据都是现有代码已经或可以安全获取的真实字段，不新增未经确认的 API。

### 2.2 单项得分（0–100，鲁棒 + 可解释）

对每个维度 `i`，原始值 `x_i ≥ 0`：

```text
l_i   = ln(1 + x_i)                 # 对数压缩，体现边际递减
ref_i = 稳健参考上限（见下）
sub_i = clamp(l_i / ref_i, 0, 1) * 100
```

- `ref_i` 取当前世界中 `l` 的**缩尾上限**：国家数 N ≥ 20 时取 95 分位数，N < 20 时取最大值。目的：避免一个极端强国把其余国家全部压成接近 0，提升公平性。
- 若 `ref_i ≤ 0`（该维度所有国家都是 0），`sub_i = 0`（修复 L1，不再出现“无差异却得 50 分”）。

**为什么用对数**：人口/领土/经济等跨多个数量级，直接归一化会让大数值决定一切；`ln(1+x)` 把“从 100 到 1000”和“从 1000 到 10000”都映射成近似等距的增量，体现边际递减。

**为什么用缩尾参考而不是 min-max**：min-max 的 `max` 若被单一异常值拉高，会把所有国家压缩到低分区；缩尾参考对极端值更稳健，且世界规模变化时不会因为出现一个巨国导致全员分数暴跌。

**局限**：缩尾参考仍是「相对当前世界」的尺度，国家分数会随世界整体发展而相对变化（这是排行榜的固有特性，不是缺陷，但需在 UI/文档说明）。

### 2.3 总分（0–100）

```text
total = Σ w_i * sub_i          # Σ w_i = 1，权重可配置
```

**建议默认权重（提案，非“正确答案”）**：

| 维度 | 建议权重 | 理由 |
| --- | --- | --- |
| military | 0.20 | 能力类，影响战争与安全 |
| economy | 0.20 | 资源/财富类 |
| population | 0.15 | 规模类 |
| territory | 0.15 | 规模类 |
| development | 0.15 | 规模/城市化类 |
| influence | 0.15 | 声誉类 |

**关于相关性与重复计分**：`population / territory / development` 三者高度相关，都近似度量“规模”，合起来占 45%。这是有意保留六个维度的代价，**必须在文档中明示**，避免用户误以为六个维度彼此独立。缓解方式二选一（设计为可选配置）：

- 默认：算术加权和（最可解释，每项贡献 = 权重 × 分项分）。
- 可选：几何平均 `total = 100 * Π (sub_i + ε)^w_i`（对“偏科”国家更严格，防止用单项超高掩盖多项落后），需加 ε 处理 0 分。

**默认仍用算术加权和**，因为可解释性优先；几何平均作为后续可选开关，避免一开始过度复杂。

**权重可调性**：沿用现有 `PowerRanking.weights.txt` 机制，键扩展为 6 个：`military / economy / population / territory / development / influence`；读入后做 `max(0, v)` 截断再归一化（修复 L2），并保留对旧键 `cities→development`、`renown→influence` 的兼容读取。

### 2.4 缺失/异常/极端值处理

- `x_i < 0` 一律按 0 处理。
- 对象为 null（如 `kingdom.data` 为空）→ 国家跳过并记一次告警（承接审计 M1 的“不吞异常、单国隔离”原则）。
- 极端值由「对数 + 缩尾参考」双重压制，不会单点主导。
- 所有维度为零的国家：各项 sub=0，total=0，排序垫底，属合理结果。

### 2.5 总分与分项分展示

- 主列表保留「排名 / 国名 / 总分」。
- 顶部详情区由“原始值”改为“原始值 + 六项 0–100 分项分”，让总分可解释、可追溯。
- 排序仍按总分降序，排名逻辑不变。

## 3. 新架构数据流

将原先耦合的逻辑拆成四个独立步骤，全部由一次定时刷新驱动：

```text
定时器(3s, 可配) 或 手动刷新
        │
        ▼
[采集] MetricsCollector
  单趟遍历国家 → 单趟遍历城市(收集 cities/zones/warriors/buildings)
               → 单趟遍历单位(收集 economy)
               → 直接取 population / renown
  输出：List<RawMetrics>（纯数据，无 UI、无评分）
        │
        ▼
[评分] ScoreCalculator（纯函数，可单测）
  对数 → 缩尾参考 → 六项 sub_i → 加权 total
  输出：List<CountryScore>（含 total + 六项 sub + 原始值）
        │
        ▼
[排序] 按 total 降序（次关键字国名）
        │
        ▼
[视图] RankingView
  与上次结果做“签名比较”，无变化则跳过重建
  有变化：复用行对象，只更新 Text 与高亮
```

**分离收益**：采集、评分、排序、视图互不依赖，可独立测试与替换；升级算法不会改动采集/UI，反之亦然。

## 4. 性能优化方案

1. **单趟采集**：城市只遍历 1 次，单位只遍历 1 次（修复 M2）。注意：`population` 仍调用 `getPopulationPeople()` 一次（其内部有“有船回退”逻辑，避免自行复刻导致数值差异）。
2. **评分纯函数 + 预分配**：评分阶段只用定长数组/复用的 `List`，不新建临时 `List/Dictionary`；避免 LINQ 与字符串拼接热路径。
3. **变更检测缓存**：对排序后的 `List<CountryScore>` 生成轻量签名（如每个国家 `id:total` 的拼接或哈希）；世界稳定时签名不变，跳过 UI 重建。这是最主要的 UI 开销削减点（承接 M3）。
4. **UI 行复用**：缓存行对象池，刷新时只更新 `Text.text` 与选中高亮，不再每 3 秒销毁重建全部行（修复 M3）。
5. **刷新仍定时**：不每帧计算；默认 3 秒，可配置。未来可选：通过 NML 事件系统订阅王国/城市变化做脏标记，本期不做（避免过度复杂）。
6. **异常隔离**：采集阶段对单国 `try/catch` + `LogWarning`，跳过坏国继续（修复 M1，不吞异常）。

---

## 5. 与现有代码的兼容性风险

1. **权重文件格式**：`cities/renown` → `development/influence`。需兼容旧键，否则老用户配置失效。属低风险，但需迁移说明。
2. **UI 详情区**：从“原始值”改为“原始值+分项分”，属于显示增强，不影响主列表与 F8。
3. **采集口径一致性**：合并遍历时，`zones/warriors/buildings/population` 的累计口径必须与现有 `countXxx()` 完全一致，否则分项数值会漂移。实现时需逐一核对 `City.countZones()`、`City.countWarriors()`、`City.buildings.Count`、`City.getPopulationPeople()`。
4. **缩尾参考改变绝对分数**：升级后所有国家总分与旧版不可直接对比（这是算法变更的必然结果，需在更新日志说明）。
5. **无 Harmony/无原版改动**：继续保持，不引入新的补丁冲突面。
6. **异常隔离不吞异常**：只隔离单国采集，评分/排序异常仍需上抛，避免掩盖 bug。

## 6. 分阶段实施计划

**阶段 A：数据采集与异常隔离（性能基础）**
- 新增 `MetricsCollector`，单趟遍历城市/单位；`Compute` 改为调用采集器。
- 单国 `try/catch` + 告警。
- 权重文件扩展到 6 键 + 负值截断 + 旧键兼容。
- 不改变评分公式与 UI（此阶段分数应与旧版在数值上尽量一致，仅合并遍历）。

**阶段 B：新评分算法（纯函数）**
- 新增 `ScoreCalculator`，实现对数 + 缩尾参考 + 加权求和。
- `CountryScore` 增加 6 个分项分字段。
- 保持排序按总分降序。

**阶段 C：UI 刷新优化**
- `RankingView` 行复用 + 签名变更检测。
- 详情区显示分项分。
- 关闭按钮绑定修复（M4，先实机确认）。

**阶段 D：收尾**
- 兼容旧权重键、日志、文档、更新日志。
- 可选：几何平均聚合开关（延后，若需要）。

## 7. 每阶段测试标准

- **阶段 A**：同一存档下，升级前后六项“原始值”完全一致；打开排行榜刷新正常；构造国家灭亡/异常场景仅出现单国告警、排行榜仍刷新。
- **阶段 B**：分项分与总分均在 0–100；零值国家 total=0；出现一个极端强国时其余国家分数不被压缩到接近 0；单国/无国家世界表现合理；权重文件 6 键生效且负值被截断。
- **阶段 C**：世界静止时重复刷新不重建行对象（可用计数器/日志验证）；频繁开关与滚动流畅；点击行高亮切换正常；X 按钮正确关闭本窗口；详情区显示 6 项分项分。
- **阶段 D**：旧 `cities/renown` 权重键仍可读取；长时间运行内存/GC 不持续增长；与其它模组共存无冲突。

## 8. 需要你确认的设计决策

1. 六个维度定义（尤其 `development = 城市数 + 建筑数`、`influence = renown`）是否认可。
2. 默认权重方案（20/20/15/15/15/15）是否作为起点，后续再按实际表现调优。
3. 总分聚合默认用「算术加权和」（保留可解释性），几何平均只作为后续可选开关。
4. 阶段 A 先做「性能 + 异常隔离」但评分公式暂不变，是否接受这种“先架构、后算法”的顺序。
